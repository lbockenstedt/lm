# cppm — ClearPass NAC

Aruba ClearPass Policy Manager spoke. Repo: `cppm`. `module_type = "nac"`. See [architecture-topology.md](architecture-topology.md).

## Role & module_type

NAC spoke — endpoint auditing, session/access-tracker monitoring, and a hub-orchestrated IPAM→ClearPass endpoint sync. Source for the realtime NAC→IPAM reverse sync (`CPPM_GET_RECENT_SESSIONS` → `NETBOX_SYNC_ACCESS_TRACKER` on the netbox spoke).

## What it does

cppm is the Network Access Control (NAC) integration for Aruba ClearPass Policy Manager: it audits known endpoints, shows Access Tracker authentications started in the last 24 hours (including completed sessions), and keeps ClearPass and NetBox in sync in both directions — pushing IPAM-known endpoints into ClearPass ahead of auth, and pulling recently-authenticated sessions back into NetBox so the inventory reflects what's actually on the network.

In the WebUI this shows up under the **Security/NAC** area — a "NAC (Aruba ClearPass Policy Manager)" module tile, plus tabs for NAC Status, Access Tracker, My Devices, and Unknown Devices; Setup has a "NAC / ClearPass Instances" tile for connecting a ClearPass server, and System → Sync has the IPAM↔NAC sync schedules.

## Entrypoints

`python3 -m src.control_plane` (`CPPMControlPlane`); spoke `CPPMSpoke` (**no base class** — not `BaseSpoke`); falls back to `run_standalone_mode()` (FastAPI `0.0.0.0:8000`, `/status`) if `--hub` omitted. systemd `lm-cppm.service`. Installer `install.sh` (clones to `/opt/lm/cppm`, venv, `.env`, unit; `PYTHONPATH=$INSTALL_DIR:$INSTALL_DIR/core/src:$INSTALL_DIR/cppm/src`). `src/main.py` is a standalone demo script, not the entrypoint.

> **Primarily a role now.** cppm runs mainly as the **`cppm`** role hosted by the agent (`agent-<hostname>`, unit `lm-agent`): the agent opens a sub-spoke `{agent}-cppm` (module_type `nac`, parent-auto-approved) and self-installs it via `agent/src/agent_spoke.py::_install_role` (clones `lbockenstedt/cppm.git` + deps); because `CPPMSpoke` is non-BaseSpoke the role loader wraps it with `_RoleAdapter`. The dedicated `lm-cppm.service` / `install.sh` `cppm-spoke-1` path is the **legacy/standalone** alternative. Connection config (`CPPM_HOST`/creds) comes from the hub push (WebUI), not a per-module `.env`.

## Ports / backends

Talks to ClearPass REST (`CPPMClient`, `src/client.py`, `requests.Session`, TLS verify off). Auth: OAuth2 (`POST /api/oauth`) with **password grant preferred over client_credentials** when user creds are available (inherits the user's operator profile vs the API client's restricted profile); falls back to basic auth. Token cached with expiry (`expires_in`, 30s skew). Endpoints: `/api/session` (access tracker / recent sessions / user sessions / NAC status), `/api/endpoint` (device DB, by-MAC, by-IP, upsert/sync), `/api/role`. Standalone mode serves :8000.

`.env.example` (loaded by `client.py`'s hand-rolled `load_dotenv()`): `CPPM_HOST`, `CPPM_CLIENT_ID`, `CPPM_CLIENT_SECRET`, `CPPM_USER`, `CPPM_PASS`; plus `SPOKE_ID`, `SPOKE_SECRET`, `HUB_URL`. Connection config also pushable via `UPDATE_CONFIG`.

## Install flags

`install.sh`: `--hub`, `--id`/`--name`, `--secret`, `--hub-secret`, `--all-prereqs` (no-op). Keeps default PSK `lm-secret` for zero-touch.

## Key commands / handlers (`spoke.handle_command`, via `run_in_executor` — `CPPMQueries` is sync `requests`)

`GET_VERSION`, `CPPM_REFRESH_CACHE`, `UPDATE_CONFIG`, `TEST_AUTH` (tries every OAuth candidate, reports per-attempt), `PROBE_API` (raw `_request`). Cached: `CPPM_GET_ACCESS_TRACKER`, `CPPM_GET_DEVICE_DATABASE`, `CPPM_GET_NAC_STATUS`. Live: `CPPM_GET_RECENT_SESSIONS` (last `lookback_minutes` default 2 — **not cached**, time-sensitive, called ~60s by the hub realtime NAC→IPAM loop), `CPPM_GET_SYSTEM_HEALTH`, `GET_DEVICE` (by MAC), `LIST_ENDPOINTS`, `GET_ENDPOINT_DETAIL`, `GET_DEVICE_SESSIONS`, `GET_USER_SESSIONS`, `GET_LOGS` (auth logs by start/end), `LIST_ROLES` (optional `prefix` filter, paged), `SEARCH_SESSIONS`, `CPPM_SYNC_ENDPOINTS` (hub-orchestrated IPAM→ClearPass: upserts a tenant's endpoint batch tagged `NetBox_Tenant_Name`/`_ID` + `Tenant` + `IP Address`/`Hostname`/`status:Known`, plus `LM_Role` from `nac_role` (a role change bounces the session); `replace=True` deletes endpoints previously tagged with this tenant absent from the batch; MAC-keyed upsert with IP fallback; IP-only records with no existing endpoint skipped; per-endpoint failures counted, never raised).

## Notable behaviors & gotchas

- **`CPPMSpoke` is non-BaseSpoke** — `class CPPMSpoke:` (no `BaseSpoke` base). Implements `spoke_id`/`config`/`get_version`/`handle_command` itself; registered into the control plane's `modules` dict. The control plane also locally overrides `register_module` (same pattern as ldap). On the hub side, the agent-spoke role loader wraps it with `_RoleAdapter`.
- **Endpoint IP fallback scan** — ClearPass's `ip_address` filter only matches the first-class field; `_endpoint_ips` collects IPs from arbitrary attribute names and `_build_ip/mac_endpoint_map` do bounded paged scans (`ENDPOINT_SCAN_CAP` / a larger sync cap) so static-IP devices whose IP lives under a profiler-populated attribute are still matched and their MAC reused.
- **In-memory cache** for `CPPM_GET_ACCESS_TRACKER`/`CPPM_GET_DEVICE_DATABASE`/`CPPM_GET_NAC_STATUS` only; `CPPM_GET_RECENT_SESSIONS` deliberately uncached (realtime loop).
- **Access Tracker history** — `CPPM_GET_ACCESS_TRACKER` without `lookback_hours` stays active-only for dashboard counts. The hub's Access Tracker page query (`ACCESS_TRACKER_QUERY` in `routes/cppm.py`) sends `lookback_hours=24` to include sessions started during the prior 24 hours, whether active or closed. The NAC cache feed fixes one UTC upper timestamp, gathers up to ten 1,000-row pages per source, and stores the merged snapshot under one cache key with a five-minute minimum refresh interval. Login kicks, manual cache refreshes, endpoint-sync refreshes and page views all honor that floor, which counts from the last query whether it succeeded or failed. Inside the floor the page shows the last snapshot; when nothing is cached yet, the route answers 503 with a `Retry-After` header (admins see the last error and the wait, other users the hub's generic 503 message). Every NAC cache feed pass (about every 10 seconds, the first right after hub startup) drops Access Tracker cache entries in an earlier shape (per-page, admin fan-out, global or older-snapshot keys). A manual CPPM refresh targets only the selected tenant's history snapshot. The route requires tenant context, filters the cached records by the resolved tenant, sorts by session time, and then applies the visible page offset/limit. A warning appears if a source reaches the 10-page safety cap. Older spokes ignore the optional field and return active sessions only until updated. The CPPM spoke's paged snapshot contract shipped separately in commit `c552cba`.
- **Which ClearPass answers**
  - **A tenant's NAC pages** read its own ClearPass, plus the shared tenant's ClearPass while a shared tenant is configured and the tenant still uses shared NAC. With shared access `auto`, a tenant stops using the shared ClearPass as soon as it has a NAC instance record of its own (bound to any spoke or to none) or a NAC spoke bound to it, even while that spoke is offline. One-spoke reads (dashboard counts, global search, the ClearPass policy in VM details, a device's detail and sessions, the ClearPass logs) use the first of those, filtered by the tenant's subnets when it is the shared one. NAC Status totals and the ClearPass role list cover every tenant on an appliance and have no rows to filter, so they come only from the tenant's own ClearPass (for the shared tenant, the shared one); a tenant on the shared ClearPass gets a 403 there and its NAC Status tiles keep their "—" placeholder. Endpoint and NAD sync write by the same rule: a tenant's own ClearPass, else the shared one only while the tenant still uses shared NAC, so while a tenant's own spoke is offline its sync reports "… or CPPM spoke not connected" instead of writing to the shared ClearPass. 802.1X JIT creates ClearPass users only on the tenant's own ClearPass (for the shared tenant, the shared one). A tenant on the shared ClearPass gets an error that says so: ClearPass local users are keyed by username alone, so one tenant's JIT user would overwrite or delete another tenant's user of the same name.
  - **Which spoke is a tenant's own** is decided by the NAC instance records the hub pushes to it, whatever the spoke's own binding says (a record moved to another spoke in Setup → NAC keeps its tenant). A spoke's records are the ones bound to it or, if none is, the first record with no spoke, which the hub pushes to every NAC spoke with no record of its own when it connects. A spoke whose records all belong to one tenant is that tenant's own: the tenant reads it without its subnet filter (so the dashboard counts every session on it), and only that tenant and Global Admins see it in the navigation. A spoke no record configures follows its binding. A tenant's records are tried in config order, then the spokes bound to it, with spoke ids sorted so the pick does not flip with connection order.
  - **Spokes no one tenant owns.** A spoke pushed two tenants' records, or a tenant's record next to a shared or hub record (blank or ADMIN), or bound to a tenant but pushed the hub's record (a record with no tenant, or the legacy single config), serves no one tenant alone. No tenant uses it, and only a Global Admin reads it (with no tenant selected) or writes to it. A tenant whose own ClearPass is in that state gets none, because it still counts as having its own and so does not fall back to shared, until the records are fixed in Setup → NAC. A spoke pushed only shared records is the shared ClearPass, filtered by subnet for every tenant. Each of its rows (an authentication, endpoint, device record or log line) is shown, and counted on the Dashboard, only for the tenant with the most specific prefix holding one of the row's addresses, among the prefixes the shared ClearPass serves: a tenant's own-VRF prefixes and the shared tenant's prefixes don't count, and a tie shows the row to both tenants. So a tenant with `10.0.0.0/8` does not see the authentications of a tenant with `10.1.0.0/16`. Tenant groups are narrowed like their members; the shared tenant is not narrowed.
  - **No tenant selected.** An admin's one-spoke reads and the role-override list use the shared tenant's ClearPass, else a connected, approved spoke no real tenant owns (lowest spoke id first). Unassigned, shared and ADMIN bindings and records own nothing. Shared writes (endpoint and NAD sync, 802.1X JIT for the shared tenant) use the shared tenant's ClearPass when one is configured, with no substitute while it is offline, and that unowned spoke otherwise. A ClearPass a real tenant owns never answers for another tenant or for the global view. In an admin's merged NAC lists (no tenant selected), each row is labelled with the tenant whose ClearPass answered (`get_nac_spoke_owner`), not with the spoke's binding, so a tenant's record moved onto a spoke bound to another tenant keeps its own tenant's label. Rows from the shared ClearPass get the shared tenant's label, and rows from a ClearPass no tenant owns get none.
  - **Every NAC save re-sends every spoke.** Adding, editing, moving or deleting a NAC instance record (Setup → NAC or Tenant Devices) re-sends every connected, approved NAC spoke its config, not only the record's own spoke, and each spoke is re-sent its config when it connects. The hub remembers which record and host each spoke confirmed it holds (`nac_config_pushed` in the hub state, kept across hub restarts). A push counts only once the spoke answers SUCCESS: a spoke that refuses the config (its command queue is full) or does not answer within 20 seconds still holds its old one, and a SUCCESS from a connection the spoke replaced while the hub waited does not count, because the new connection is a new process. While a different config is on its way, the spoke is stale (see below) until it confirms it. Pushes to one spoke run one at a time and each sends the config as it is when it runs, so a spoke never ends on an older config than the last save. A save sends every spoke its config at once (at most 8 at a time) and waits for the answers; a spoke that does not confirm stays stale until its next reconnect or NAC save. A cppm spoke keeps the last config it was sent and has no command to forget it, so a spoke whose record was moved away or deleted, with no other record to be sent instead, keeps answering from that record's ClearPass. That spoke is stale: NAC reads and writes skip it, including the realtime sync and a Global Admin's merged views, only a Global Admin with no tenant selected sees it in the navigation, and the hub logs that it may still hold the old ClearPass. It serves again once the hub sends it a config: bind a NAC record to it, or add a record with no spoke, in Setup → NAC. Deleting the spoke from the hub also forgets what it was sent. With no NAC record at all, every NAC spoke is sent the legacy single ClearPass config (`global_config["cppm"]`) instead, and the hub tracks it the same way, as its own record with no spoke and no tenant: a spoke is stale until it confirms the config's current host, so a reconnect or a host change it did not confirm keeps it out of NAC reads and writes, and a spoke bound to a tenant that holds it serves the hub's ClearPass, not the tenant's (see *Spokes no one tenant owns*). A spoke a NAC record configures is also stale until it confirmed that record's id and host: until then it may still answer from a ClearPass set up in its own `.env`, or from another record. A record with no host is never sent, so its spoke stays stale until the host is set. A spoke that connects is a new process, which holds only its `.env` config, so a spoke the hub had sent a config is stale from the moment it connects until it confirms the config it is sent then. The hub sends it at once, and again after 30 seconds and after 2 more minutes while the same connection is up and the spoke is still stale; after that, the next reconnect or NAC save sends it again. Opening Setup → NAC moves a legacy single ClearPass config (`global_config["cppm"]`) into a NAC record with no spoke, and sends it to the NAC spokes at once. Upgrade note: a hub upgraded from a release without this rule has no record of what it sent, so every spoke a record or the legacy config configures is skipped until it reconnects after the hub restart and confirms its record. The save reply's `pushed` says whether a spoke confirmed the saved record's own config; on delete, whether the record's spoke confirmed a new config.
  - **The legacy `POST /setup/cppm-config`** (one hub-wide ClearPass config; no WebUI page calls it). While any NAC instance record exists it answers 409 and saves, sends and drops nothing: each spoke is sent its NAC instance record, so the legacy config would change nothing a spoke uses. Edit the records in Setup → NAC instead. With no record, it saves the config and re-sends every connected, approved NAC spoke its config, as a NAC save does (each is sent the legacy config, as on connect), then drops the cached NAC lists. A spoke that does not confirm it stays stale until a later save or reconnect sends it again. The reply's `pushed` is true when a spoke confirmed the config, as for a NAC record save: not when no NAC spoke is connected, the config has no host, or no spoke confirmed it.
  - **Cached NAC lists follow ownership.** Every NAC cache key (device list, Access Tracker, NAC Status, role list) ends in `src=<fingerprint>`, a short hash of the saved settings that decide which ClearPass answers for whom (`nac_cache_fingerprint` in `routes/cppm.py`): each NAC instance record's tenant and host (or the legacy single ClearPass host), each NAC spoke's tenant binding, and which tenants are shared or set a shared access other than `auto`. A change to any of these gives new keys, so the next page view or feed run reads every NAC list again, and the Access Tracker's five-minute floor starts over. An entry cached under the old settings is never read again, even when a hub crash lost the drop that followed the change.
    - **What changes the keys:** adding or deleting a NAC instance record or changing its tenant or host, binding a NAC spoke to another tenant, a NAC spoke's first connection or its deletion from the hub, a new legacy cppm-config host, and a tenant write that changes which tenant is shared or a tenant's shared access.
    - **What keeps them:** the fingerprint leaves out which spoke a record is on and which spokes are connected. Instance failover, which moves a record to another spoke but keeps its tenant and its ClearPass, re-binding a spoke to the same tenant (every PSK reconnect does) and a hub restart keep the cached lists. The NAC Status key also names the ClearPass the hub sends its spoke (`nac_status_key`), so a spoke that now holds another ClearPass reads its totals again.
    - **No fetch stores data under an old key.** A NAC fetch checks the fingerprint again just before it asks a spoke, on every page of an Access Tracker scan, and answers 503 "NAC settings changed; retry" if it changed. The next read or feed pass uses the new key.
    - **Cleanup.** Each NAC feed pass first drops the cached keys no current read uses (`drop_orphan_nac_caches`). A NAC record save, binding a NAC spoke to another tenant, a legacy cppm-config save, and a tenant write that changes sharing or deletes a tenant (Setup → Tenants, `POST /api/tenant/{tenant}`, the test feed's shared-tenant mirror, and the NetBox sync pruning a tenant group that left NetBox) also drop every NAC entry at once (`drop_nac_caches`), which detaches the fetches still running under the old settings.
    - **Not covered:** a ClearPass that a spoke reads from its own `.env`, changed outside the hub.
  - **Tenant admins cannot unbind** a NAC, IPAM or directory instance or a network device in Tenant Devices (403), because the hub pushes a record with no spoke to spokes outside the tenant. A Global Admin can. A tenant admin can still unbind (park) a firewall.
- **Token strategy** — password grant with `client_id` (configured, then `ClearPass`), then password grant with no `client_id`, then `client_credentials` (user operator profile > API client profile). Tolerates empty 204 bodies on DELETE.
- **`CPPM_SYNC_ENDPOINTS` tenant tagging** uses the same attribute names the at-auth-time Context Server Action uses (`NetBox_Tenant_Name` etc.) so an Enforcement Policy matches the tenant whether the endpoint was synced in advance or tagged at auth time.

## How it works

- **Connection config comes from the hub push, not a `.env`.** `UPDATE_CONFIG` carries `host`/`user`/`password`/`client_id`/`client_secret`; the spoke calls `CPPMClient.update_config()`, which clears any cached OAuth token so the next request re-authenticates against the new config. `CPPM_HOST`/`CPPM_CLIENT_ID`/`CPPM_CLIENT_SECRET`/`CPPM_USER`/`CPPM_PASS` env vars / `.env.example` are only a bootstrap fallback for standalone/dev use.
- **OAuth token strategy.** ClearPass's `/api/oauth` is tried with a preference order, not a single fixed grant: if user credentials are configured, **password grant is tried first** — once with the configured `client_id` (if any), then again with `client_id="ClearPass"`, then with no `client_id` at all — because password grant inherits the authenticating user's own operator profile rather than the API client's (often more restricted) profile. `client_credentials` (client_id + client_secret) is the fallback if password grant isn't configured or fails. A successful token is cached with its `expires_in` and refreshed ~30s before expiry. `TEST_AUTH` runs through every candidate and reports the outcome of each attempt individually, rather than just the first success/failure — this is the fastest way to see exactly which grant type ClearPass is accepting or rejecting.
- **Cached vs. live reads.** Access Tracker reads a tenant-scoped hub snapshot covering the prior 24 hours, regardless of the visible table page; the hub scans up to ten 1,000-row pages per source and enforces a five-minute minimum refresh interval. If one source fails, the page warns that results and counts may be incomplete; if all sources fail, the last successful snapshot stays cached and ClearPass is not queried again until five minutes after the failed query. Device Database and NAC Status use their cache-backed default views; other paged/filtered routes may fetch live data, depending on the route.
- **`CPPM_GET_RECENT_SESSIONS` is deliberately never cached** — it's a realtime pull of sessions started in the last `lookback_minutes` (default 2), and it's what the hub's background **realtime NAC→IPAM reverse sync** loop calls roughly every 60 seconds (`lm/core/src/realtime_ipam_nac_sync.py`, config key `realtime_ipam_nac_sync`, loop starts ~75s after hub startup). Each cycle: pull recent sessions from every connected, approved NAC spoke that has a ClearPass configured and is not stale (tenants whose addresses overlap must each run their own ClearPass; a shared ClearPass never sees overlapping addresses) → attribute each session to a tenant: every session from a ClearPass one tenant owns (see "Which ClearPass answers") goes to that tenant, and the shared ClearPass's sessions go by NetBox prefix containment, with the spoke's binding breaking ties only when it names no real tenant. A spoke only a Global Admin reads (mixed or stale) is not pulled → push the attributed sessions to the netbox spoke via `NETBOX_SYNC_ACCESS_TRACKER` with `replace=False` (only-add-missing — NetBox stays authoritative, this sync never overwrites or deletes a hand-managed NetBox record). Sessions with no MAC are dropped before the push (nothing to match/create by); sessions whose IP falls in no tenant's prefix are dropped and counted as unattributed.
- **The forward direction — IPAM → ClearPass — is `CPPM_SYNC_ENDPOINTS`,** driven by the hub's `endpoint_sync.py` on its own schedule (config key `netbox_cppm_sync`; interval or daily-time mode). Each cycle the hub pulls a tenant's IPs from NetBox (or another registered IPAM source) and pushes the batch to the cppm spoke, which upserts each endpoint into ClearPass Device Inventory tagged with `NetBox_Tenant_Name`/`NetBox_Tenant_ID` plus a friendly `Tenant` attribute (no slug attributes; `NetBox_Tenant_ID` is the LM tenant id and decides ownership) — the same attribute names the at-auth-time Context Server Action stamps, so an Enforcement Policy matches the tenant whether the endpoint was pre-synced or tagged live at auth. Matching is MAC-first (a batch-built MAC→endpoint map avoids one HTTP round-trip per record); IP-only records are resolved by an existing ClearPass endpoint carrying that IP under any attribute name (not just the first-class `ip_address` field ClearPass's REST filter is limited to), or, failing that, a MAC borrowed from a live session whose `framedipaddress` matches. Records that still have no MAC after both attempts are skipped, since ClearPass endpoints are MAC-keyed. `replace=True` (the default) makes IPAM authoritative: endpoints previously tagged for this tenant but absent from the current batch are deleted.
- **Tenant subnets → ClearPass Network Devices (`CPPM_SYNC_NADS`).** Right after each tenant's endpoint sync the hub reads the tenant's `radius` vault secret (type *RADIUS / TACACS shared secret*, fields `radius_secret` / `tacacs_secret`, in the tenant's bucket; the default tenant also falls back to the admin bucket), collapses the tenant's NetBox prefixes to the outermost subnets and sends them to the cppm spoke. The spoke keeps one Network Device per subnet (`LM-<tenant>-<subnet>`, vendor Aruba, description `LM-managed tenant=<id>; …`) with those secrets, and deletes that tenant's LM-managed devices whose subnet is gone. Devices without the `LM-managed` marker are never touched. No secret or no prefixes → skipped. Overlapping subnets across tenants (e.g. the same RFC1918 range in two VRFs) can be rejected by ClearPass, which has one address space; the error is logged as `[sync-error] nad sync`.
- **Sync loops summary:** endpoint sync (IPAM→ClearPass, `CPPM_SYNC_ENDPOINTS`) runs on its own configurable schedule from `endpoint_sync.py`; the realtime reverse sync (ClearPass→NetBox, `CPPM_GET_RECENT_SESSIONS` → `NETBOX_SYNC_ACCESS_TRACKER`) runs roughly every 60 seconds from `realtime_ipam_nac_sync.py`. An IPAM change made through the hub (a NetBox device or IP added, edited or deleted) also starts the edited tenant's endpoint sync at once, when automatic sync is enabled and that tenant's ClearPass (its own, else the shared one while it still uses shared NAC) is on a connected, approved, configured spoke that is not stale; another tenant's spoke does not decide it. The scheduled sync runs while any NAC spoke is usable in that sense, and each tenant's sync writes only to its own ClearPass. Both are hub-scheduled — the cppm spoke itself has no timers of its own, it only answers each request when asked.
- **Every ClearPass call runs in a thread executor** (`run_in_executor`) because `CPPMQueries`/`CPPMClient` use synchronous `requests`, not async I/O — this keeps a slow/hung ClearPass call from blocking the spoke's event loop.

## How to use it

- **Connect ClearPass.** Setup → NAC / ClearPass Instances → add/edit the instance: host (hostname or IP; `https://` is assumed if omitted), plus either an API client id/secret, or a username/password (or both — password grant is preferred automatically when both are present). Saving pushes `UPDATE_CONFIG` to the connected cppm spoke immediately and waits for it to confirm.
- **Supply the secret from the Credential Vault (optional).** Instead of typing the secret inline, pick a Credential Vault secret on the instance so the plaintext never lands in `global_config`. Store a **Login** secret in the vault and tick **"OAuth2 account (ClearPass)"** to store it as an OAuth2 API client (Client ID + Client secret, `grant_type=client_credentials`); leave it unticked to store a username/password login (password grant). At push time the hub overlays the resolved secret onto the instance — the OAuth account fills `client_secret`, a plain login fills `user`/`password` — so ClearPass picks the matching grant. (Client ID stays on the instance form; it is not a secret.)
- **Verify the connection is actually working.** Use TEST_AUTH (exposed as a "Test" / "Test Auth" action against the instance) — it tries every OAuth candidate ClearPass would accept given the configured credentials and reports each attempt's HTTP status/response individually, so you can see exactly which grant type is failing rather than a single opaque error.
- **View Access Tracker records.** The page shows authentications started in the last 24 hours, including completed sessions. Global admins must switch into a tenant before viewing its records; the unselected all-tenant session view is disabled.
- **Force a fresh pull of endpoints/sessions/status** instead of waiting on the cache: use the refresh action tied to `CPPM_REFRESH_CACHE`. Access Tracker refreshes its tenant-scoped snapshot through the hub cache and honors the five-minute minimum interval; other paged/filtered routes may fetch live data depending on the route.
- **Trigger an IPAM→ClearPass endpoint sync on demand** for one tenant or all tenants from System → Sync's endpoint-sync card — this runs `CPPM_SYNC_ENDPOINTS` immediately instead of waiting for the scheduled interval/daily time. `POST /admin/ops/endpoint-sync {"tenant_id"}` does the same for one tenant and also runs the Network Device (`CPPM_SYNC_NADS`) sync.
- **Trigger the realtime NAC→IPAM reverse sync on demand** ("Sync now" on the realtime NAC→IPAM card in the same System → Sync area) to pull the last `lookback_minutes` of sessions and push newly-seen devices into NetBox right away.
- **Look up a specific device or session**: use My Devices / Unknown Devices / Access Tracker tabs, which map to `GET_DEVICE`/`GET_ENDPOINT_DETAIL` (by MAC), `GET_DEVICE_SESSIONS`/`GET_USER_SESSIONS`, and `SEARCH_SESSIONS`/global search respectively.

## NAC role override (`LM_Role`)

Pick a ClearPass role for one device so ClearPass hands back a different VLAN or policy (DMZ, ROUTED, and so on).

- **Where:** NetBox → IP Addresses → Edit → **NAC Role Override**. The dropdown lists every ClearPass role whose name starts with `SSPLM-`. There is one list for everyone, read from the configured shared NAC spoke, or from a spoke no real tenant owns (see *Which ClearPass answers*) when no shared source exists; a spoke a tenant owns is never used as a global fallback. The choice is saved on the IP as the NetBox custom field `nac_role`.
- **Role list cache:** `GET /api/cppm/role-overrides` (`LIST_ROLES {"prefix":"SSPLM-"}`, cache namespace `nac_role_overrides`). It's refreshed by the NAC cache feed and shows a stale badge if ClearPass is unreachable. `POST /api/cppm/role-overrides/refresh` re-reads it immediately (the **Refresh** button). If you add a new `SSPLM-` role in ClearPass, it appears here on the next refresh.
- **Push:** saving the IP re-syncs that tenant's endpoints. Each endpoint record carries `nac_role`, and the cppm spoke writes it to the endpoint attribute `LM_Role`, or removes the attribute when the role is cleared. The spoke creates `LM_Role` in the Endpoint dictionary the first time it's needed. Records without a `nac_role` key (older hubs) leave `LM_Role` untouched.
- **Bounce:** when `LM_Role` changes on an endpoint that has a MAC, the spoke sends a RADIUS Disconnect (`POST /api/session-action/disconnect/mac/<mac>`), so the device re-authenticates and picks up the new role. This happens whether the change came from LM or from a direct NetBox edit. An unchanged role never bounces.
- **Needs a MAC:** ClearPass endpoints are keyed by MAC, so an IP with no MAC can't carry an override.
- **ClearPass side (one-time per role):** see `clearpass/README.md` → *NAC role override*.

## JIT 802.1X accounts & "My Users"

The hub's `core/src/dot1x_jit.py` broker creates just-in-time 802.1X accounts for simulation clients. Each **1X** cell in the Config/Engine SSID matrix has an **Account location** setting: Entra, LDAP (tenant OU), or ClearPass (Policy Manager local user). The cs engine sends `CS_DOT1X_PROVISION`, `CS_DOT1X_RELEASE`, and `CS_DOT1X_SYNC` messages to the hub as clients join or leave a 1X cell. For each account, the hub:

- creates the account in the cell's account location. For ClearPass this uses `CPPM_CREATE_LOCAL_USER` / `CPPM_SET_LOCAL_USER_PASSWORD` / `CPPM_DELETE_LOCAL_USER` / `CPPM_GET_LOCAL_USER`, with role `global_config.dot1x_jit.cppm_role` (default `[Employee]`).
- generates a random password and stores it in the enabled Credential Vault. With no vault enabled, it stores the password in the hub's encrypted state (`dot1x_jit_secrets`).
- sends the password to the sim client through an encrypted `CS_DOT1X_CREDENTIAL` frame. The password is redacted from logs and masked in every overrides view.

An hourly sweep handles rotation and cleanup:

- It rotates passwords every `rotate_days` (default 30).
- Every `cleanup_interval_days` (default 30), it deletes accounts that have no client assigned and have not been seen for `unused_days`.

When the engine stops assigning a client to the 1X cell, or the client is torn down, the cs engine releases the account right away. The sweep catches anything that release missed.

**NAC → My Users** lists the tenant's sim-created accounts, showing username, location, assigned hosts, and last rotated time. It offers **Reset password** and **Delete**:

- **Reset password** generates a new password, updates the vault, and sends it to the sim client.
- There is no reveal action.
- If you delete an account while a client is still assigned to its 1X cell, the engine re-creates it.

The API is `GET /api/cppm/my-users`, plus `POST /api/cppm/my-users/reset` and `POST /api/cppm/my-users/delete` (`routes/nac_users.py`).

## Troubleshooting / common questions

- **"Auth to ClearPass keeps failing — how do I tell why?"** Run TEST_AUTH. It reports every OAuth attempt tried (password grant with each candidate `client_id`, then `client_credentials`) with that attempt's actual HTTP result — an `HTTP 400`/`401` on the password-grant attempts usually means the ClearPass Guest/API Login username or password is wrong or the operator profile lacks API access; a failure only on the `client_credentials` attempt usually means the API client's client_id/secret is wrong or the client's operator profile is too restricted. Compare against what's actually configured on the ClearPass side (API Services → API Clients, and the Operator Login the username belongs to).
- **"The NAC spoke shows offline/red in Diagnostics — what breaks?"** Both sync loops (endpoint sync and the realtime reverse sync) skip a cycle cleanly when no NAC spoke is connected — they don't error loudly, they just log and wait for the next cycle. Cached reads (including tenant-scoped Access Tracker snapshots, Device Database and NAC Status) keep serving the last successful data. Access Tracker warns and marks the count as a lower bound when one source fails; a fully failed refresh leaves the previous snapshot cached; with nothing cached yet, the Access Tracker page shows an error until the five-minute floor passes. Live calls such as recent sessions and TEST_AUTH require a connected spoke.
- **"An endpoint isn't getting tagged with the right tenant / isn't showing up in ClearPass at all."** If the record only has an IP (no MAC) on the NetBox side, `CPPM_SYNC_ENDPOINTS` can only tag it if ClearPass already has an endpoint carrying that IP (under any attribute, not just the standard `ip_address` field) or a live session whose `framedipaddress` matches — check the sync's per-tenant result for a skipped count and reason. If it has neither, ClearPass has no MAC to key the endpoint on and the record is skipped; the fix is to make sure the device authenticates at least once (creating a ClearPass session/endpoint) before it can be synced by IP alone.
- **"A tenant's endpoints disappeared from ClearPass after a sync."** `CPPM_SYNC_ENDPOINTS` runs with `replace=True` by default — IPAM is treated as authoritative, so any endpoint previously tagged for that tenant but no longer present in the current NetBox batch is deleted from ClearPass. Check whether the device was removed/moved off that tenant's prefix in NetBox first.
- **"Recent sessions aren't showing up in NetBox."** The realtime reverse sync only adds — it never overwrites or deletes NetBox records, and it drops any session whose IP doesn't fall inside one of the target tenant's NetBox prefixes (check for an "unattributed" count) or that has no MAC at all. Also confirm both a NAC (cppm) spoke and an IPAM (netbox) spoke are connected — the loop needs both to run a cycle.
- **"Is cppm running as its own service or as part of the agent?"** In the current topology, cppm normally runs as the `cppm` role inside the generic `lm-agent` unit (sub-spoke `{agent}-cppm`, auto-approved by its parent, wrapped in a `_RoleAdapter` because `CPPMSpoke` isn't a `BaseSpoke`) — check Diagnostics for a spoke id like `agent-<hostname>-cppm`. The standalone `lm-cppm.service` / `install.sh` path (spoke id `cppm-spoke-1`) still works but is the legacy path; either way, connection config always arrives via the hub push, never a local `.env`.
